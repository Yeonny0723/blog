# AI는 디자인 시스템을 모른다: 사내 FDS를 MCP 서버로 연결한 이유

디자인 시스템이 있다고 해서, AI가 그 시스템을 바로 활용할 수 있는 것은 아닙니다. 최근에는 Figma 시안을 바탕으로 AI 에이전트에게 UI 구현 작업을 맡기는 경우가 많아졌지만, 실제로는 구현 능력보다 사내 UI 지식을 정확히 찾아 적용하는 과정에서 더 자주 막히는 것 같습니다.

안정적인 제품을 만드는 요소 중 하나는 사용자 요구에 대응하는 속도입니다. 그런데 AI를 활용한 UI 개발에서는 이 속도가 기대만큼 나오지 않을 때가 있습니다. 사내 디자인 시스템은 이미 존재하는데, AI는 그 시스템을 기본적으로 알지 못하기 때문입니다.

사람 개발자는 화면을 보면 자연스럽게 연결합니다. 이 버튼은 어떤 공통 컴포넌트를 써야 하는지, 이 배경색은 어떤 토큰으로 매핑해야 하는지, 아이콘 이름은 무엇인지, 비슷한 예제는 Storybook 어디에 있는지 빠르게 찾아냅니다. 하지만 AI는 사내 디자인 시스템의 이름, 규칙, 예제, 변경 이력을 기본 지식으로 갖고 있지 않습니다.

그래서 새 화면 구현을 AI에게 맡기면 실제 병목은 "코드를 짜는 능력"보다 "사내 UI 지식을 정확히 찾고 적용하는 능력"에서 발생하는 것 같습니다. 이 글은 새로운 디자인 시스템을 만든 이야기가 아닙니다. 이미 존재하는 사내 디자인 시스템 FDS를 AI가 읽고 사용할 수 있도록 MCP 서버로 연결한 과정을 정리한 기록입니다.

## 디자인 시스템이 있어도 AI 작업이 느려지는 이유

문제는 단순히 검색 시간이 늘어난다는 수준에서 끝나지 않습니다. AI가 사내 컴포넌트 구조를 모르면, 비슷해 보이는 UI를 임의로 구현하거나 존재하지 않는 props를 가정한 코드를 만들어낼 가능성이 높습니다. 그러면 사람이 다시 FDS 기준으로 검수하고, 잘못된 부분을 수정하고, 빠진 토큰을 보완해야 합니다. 결국 구현을 위임했는데도 재검수 비용이 더 커집니다.

특히 신규 화면일수록 이런 비용이 커집니다. 이미 구현된 유사 페이지가 있으면 그것을 참조하면 되지만, 새로운 디자인이 들어오면 컴포넌트 후보, 조합 방식, 색상 토큰, 아이콘 이름을 사람이 다시 설명해야 합니다. Storybook에 예제가 있어도 AI가 필요한 순간에 정확히 찾아 쓰기는 어려운 편입니다.

예를 들어 Figma에서 삭제 확인 모달 시안을 받았다고 가정해 보겠습니다. 사람 개발자는 이를 보고 `Modal`, `Button`, `Typography` 같은 후보를 바로 떠올리고, 확인 버튼에는 어떤 type을 써야 하는지, 본문 여백은 어떤 패턴을 따라야 하는지, 경고성 액션에 어떤 색상 토큰을 써야 하는지 빠르게 연결할 수 있습니다. 하지만 AI는 이런 내부 규칙을 모르면 비슷한 모달을 임의로 만들거나, 존재하지 않는 props를 넣거나, 사내 표준과 맞지 않는 색상과 아이콘을 섞어 쓸 수 있습니다.

여기서 두 가지 리스크가 함께 발생합니다.

1. 사람이 AI에게 넘겨야 하는 설명 컨텍스트가 계속 길어진다.
2. 설명이 길어질수록 AI가 잘못된 부분을 섞어 쓸 가능성도 커진다.

디자인 시스템이 계속 바뀌는 환경에서는 수동 문서만으로 최신 상태를 유지하는 것도 어렵습니다. 코드가 바뀌면 문서가 늦게 따라오고, AI를 활용하는 제품 개발자는 그 차이를 계속 추적해야 합니다. 그래서 필요했던 것은 문서를 하나 더 만드는 일이 아니라, 사내 디자인 시스템 FDS의 코드와 가이드를 단일 원천으로 유지하면서 AI가 필요한 순간 조회할 수 있는 계층을 만드는 일이었습니다.

## 핵심 문제: AI에게 필요한 것은 문서가 아니라 조회 가능한 지식 계층

(FDS는 사내 디자인 시스템을 지칭합니다.)

처음부터 목표는 새로운 디자인 시스템을 만들고 싶었던 것이 아니라, 기존 FDS를 AI가 정확히 활용할 수 있도록 만들고 싶었습니다.

여기서 중요한 판단은 FDS를 사람만 읽는 문서로 복제하지 않는 것이었습니다. README나 Storybook은 여전히 유용하지만, AI에게는 다른 형태의 인터페이스가 필요합니다. 필요한 순간에 필요한 정보만 가져와야 하고, 그 정보는 현재 코드와 어긋나지 않아야 합니다.

그래서 사내 디자인 시스템 FDS를 "문서"가 아니라 "조회 가능한 도구"로 노출하기로 했습니다. 사람이 직접 "이 버튼은 이 컴포넌트를 쓰고 props는 이렇고, 색상은 이 토큰을 쓰면 된다"고 설명하는 대신, AI가 작업 중에 직접 필요한 정보를 호출하도록 만드는 방식입니다.

이 판단을 기준으로 세운 원칙은 세 가지였습니다.

1. single source of truth는 계속 FDS 소스 코드여야 한다.
2. 사람이 수동으로 관리하는 명세가 아니라, 소스에서 자동 생성되는 지식이어야 한다.
3. 런타임 서버는 가볍게 유지하고, 무거운 분석은 빌드 단계에서 끝내야 한다.

이 원칙은 결국 "설명을 더 잘 쓰는 것"보다 "필요한 순간에 최신 정보를 정확히 꺼낼 수 있게 만드는 것"에 가까웠습니다.

## 해결 방법: FDS를 MCP 서버로 연결하기

최종적으로 만든 구조는 `FDS 소스 코드 -> generated-registry.json -> MCP server -> AI agent` 파이프라인입니다.

핵심은 FDS를 통째로 프롬프트에 넣는 것이 아니라, 소스 코드를 분석해 AI가 조회하기 좋은 레지스트리로 바꾸고, 이 정보를 MCP tool로 노출하는 데 있습니다. AI는 자연어 요청을 받으면 필요한 순간에 tool을 호출해서 컴포넌트, 훅, 색상, 아이콘 정보를 가져옵니다.

예를 들어 흐름은 이렇습니다.

1. Figma 화면에서 레이어명, 색상 값, 아이콘 토큰 같은 단서를 얻습니다.
2. AI가 이 단서를 바탕으로 적절한 FDS 컴포넌트 후보를 검색합니다.
3. 컴포넌트 상세 정보, props, 예제를 조회합니다.
4. 색상 토큰과 아이콘 이름을 FDS 기준으로 다시 매핑합니다.
5. 그 결과를 근거로 실제 UI 코드를 작성합니다.

이때 MCP 서버는 구현을 대신하는 것이 아니라, 구현에 필요한 FDS 지식을 제공하는 역할을 맡습니다. 프론트엔드 개발의 본질인 상태 관리, 데이터 흐름, 성능, 정합성, 브라우저 호환성, E2E 검증이 사라지는 것은 아닙니다. 다만 AI가 FDS 지식을 몰라서 생기던 탐색 비용과 번역 비용을 줄여주는 개입 지점이 생깁니다.

실제로는 아래와 같은 질의 흐름을 기대했습니다.

1. "삭제 확인 다이얼로그에 쓸 FDS 컴포넌트를 찾아줘"
2. `search_fds_components`로 후보를 좁힙니다.
3. `get_fds_component`로 `Modal`과 `Button`의 props, import, 예제를 확인합니다.
4. 버튼 색상이나 아이콘이 필요하면 `search_fds_colors`, `search_fds_icons`로 다시 조회합니다.
5. 조회한 결과를 근거로 UI 코드를 작성합니다.

즉 프롬프트 안에 긴 설명을 한 번에 밀어 넣는 대신, 필요한 시점에 필요한 정보만 도구로 가져오는 흐름입니다.

## 왜 정적 분석 기반 레지스트리를 만들었나

이 구조에서 가장 중요했던 부분은 FDS 소스에서 AI용 지식을 자동 생성하는 과정이었습니다.

FDS에는 이미 필요한 정보가 흩어져 있었습니다. 컴포넌트 파일에는 props 인터페이스가 있었고, JSDoc에는 설명이 있었고, Storybook에는 실제 사용 예제가 있었습니다. 아이콘 목록은 별도 맵에 있었고, 색상 시스템도 토큰 파일 안에 존재했습니다. 문제는 이 정보가 사람에게는 읽기 좋은 형태여도, AI가 즉시 쓰기 좋은 구조는 아니라는 점이었습니다.

그래서 빌드 단계에서 TypeScript AST를 정적 분석해 `generated-registry.json`을 만들도록 했습니다. 런타임에서 무거운 파싱을 반복하지 않고, 한 번 생성한 구조화된 결과를 서버가 읽도록 한 것입니다.

이 방식으로 다음 정보를 추출했습니다.

- 컴포넌트: props, 설명, 사용 예제, 관련 subcomponent
- 훅: parameter, return type, 설명
- 아이콘: variant별 label 목록
- 색상: 카테고리별 토큰과 검색 가능한 값

이렇게 하면 "문서를 갱신한다"는 개념보다 "소스가 곧 지식 베이스가 된다"는 구조에 가까워집니다. FDS 코드가 바뀌면 레지스트리만 다시 생성하면 되고, AI는 항상 최신 구조를 조회하게 됩니다.

물론 이 과정이 항상 매끄럽기만 했던 것은 아닙니다. 소스에서 자동으로 정보를 추출하려면, 먼저 FDS 코드 구조와 export 방식, Storybook 예제 품질이 어느 정도 일관되어 있어야 했습니다. 사람이 읽을 때는 큰 문제가 없어 보이던 차이도, 정적 분석이나 자동 추출 관점에서는 바로 예외 케이스가 되곤 했습니다.

또 하나 느낀 점은 AI에게 중요한 것은 "정보를 많이 주는 것"보다 "지금 쓸 수 있는 정보를 정확히 주는 것"이라는 점이었습니다. 처음에는 더 많은 정보를 한 번에 노출하는 방향도 생각했지만, 실제로는 목록 조회, 검색, 상세 조회를 나눠 필요한 시점에 필요한 정보만 가져오게 하는 편이 더 안정적이었습니다.

Figma 토큰과 코드 토큰을 연결하는 과정도 생각보다 예민했습니다. 사람은 이름이 조금 달라도 맥락으로 보완할 수 있지만, AI는 이런 차이에서 정확도가 바로 흔들릴 수 있었습니다. 그래서 단순히 데이터를 모으는 것보다, 검색과 매핑이 잘 되는 형태로 정리하는 작업이 더 중요했던 것 같습니다.

## Storybook을 사람이 아닌 AI를 위한 예제 소스로도 활용했다

이 작업에서 특히 흥미로웠던 부분 중 하나는 Storybook의 역할을 다시 정의한 점이었습니다.

보통 Storybook은 사람이 컴포넌트를 탐색하고 확인하는 문서에 가깝습니다. 하지만 AI 관점에서 보면 Storybook은 "어떻게 써야 하는지 보여주는 검증된 예제 저장소"이기도 합니다. 단순 props 정의만으로는 실제 코드 생성 품질이 충분히 올라가기 어렵습니다. 어떤 조합으로 쓰는지, 어떤 상태 흐름과 함께 쓰는지 예제가 함께 있어야 합니다.

그래서 `index.stories.tsx`에서 args 기반 예제와 render 예제를 추출하고, 가능하면 상태 변화가 포함된 예제를 우선 사용하도록 했습니다. 예를 들어 Dialog 계열 컴포넌트는 정적인 한 줄 예제보다 `useState`와 함께 열고 닫는 흐름이 있는 예제가 실제 구현에 더 유용한 것 같습니다.

이렇게 하면 AI는 단순히 "이 컴포넌트는 이런 props를 받는다" 수준이 아니라, "실제로는 이런 패턴으로 함께 사용된다"는 문맥까지 가져갈 수 있습니다.

## Figma 토큰과 코드 토큰 사이에 번역 계층을 뒀다

실제 화면 구현에서 자주 마주치는 또 다른 문제는 Figma와 코드의 언어가 다르다는 점입니다.

디자인에서는 `ic/fill/check circle`, `--Color-bg-interactive-brand-secondary`, `#E8F3FF` 같은 값이 보입니다. 하지만 코드에서는 이를 FDS 아이콘 이름이나 색상 토큰으로 다시 연결해야 합니다. 사람은 보고 유추할 수 있지만, AI는 이 번역 계층이 없으면 정확도가 크게 떨어질 수 있습니다.

그래서 아이콘과 색상 도구는 단순 조회가 아니라 "검색과 변환"에 가깝게 설계했습니다.

- 아이콘 검색은 Figma 토큰 형태와 일반 키워드를 모두 처리합니다.
- 색상 검색은 CSS 변수명, hex 코드, 속성값 기준 검색을 모두 받습니다.
- Figma MCP에서 얻은 단서가 있으면 그 정보를 바로 FDS 탐색에 연결할 수 있습니다.

이 지점 덕분에 AI는 정확한 컴포넌트 이름을 몰라도 화면 단서와 의도를 기반으로 사내 표준에 가까운 결과를 낼 수 있습니다.

## Tool 설계에서는 조회와 검색을 분리했다

MCP tool은 총 10개로 구성했습니다. 컴포넌트, 훅, 색상, 아이콘을 각각 별도 도메인으로 나누고, 각 도메인 안에서도 목록 조회, 상세 조회, 검색을 분리했습니다.

이렇게 나눈 이유는 단순합니다. AI가 항상 정확한 이름을 알고 시작하지는 않기 때문입니다.

예를 들어 어떤 경우에는 "삭제 확인 다이얼로그"처럼 의도만 있고 이름을 모릅니다. 이때는 검색이 먼저 필요합니다. 반대로 이미 `Modal`이라는 이름을 알고 있으면 상세 조회가 바로 더 효율적입니다. 색상과 아이콘도 마찬가지입니다. 어떤 때는 전체 체계를 보고 싶고, 어떤 때는 화면에서 보이는 단서 하나를 즉시 토큰으로 바꾸고 싶습니다.

도구를 세분화한 덕분에 AI는 지금 필요한 행동만 선택할 수 있게 됐습니다.

- 전체 목록을 훑습니다.
- 키워드로 후보를 좁힙니다.
- 정확한 이름으로 상세 정보를 확인합니다.

이 분리는 프롬프트를 길게 쓰는 것보다 더 효율적이었습니다. 설명을 한 번에 다 주입하는 대신, 작업 흐름에 따라 필요한 정보만 호출하게 만들 수 있었기 때문입니다.

## 기존 디자인 시스템을 바꾸지 않고 읽는 계층만 추가했다

이 프로젝트에서 의도적으로 피한 것이 하나 있습니다. FDS 자체를 MCP 친화적으로 다시 설계하지 않는 것이었습니다.

이미 운영 중인 디자인 시스템을 AI 활용을 위해 뒤엎는 것은 비용이 크고, 팀 전체 워크플로우도 흔들 수 있습니다. 그래서 기존 export 구조, 컴포넌트 파일, Storybook, 아이콘 맵, 색상 토큰을 그대로 두고, 그 위에 AI가 읽을 수 있는 계층만 얹는 방식을 택했습니다.

이 선택으로 얻은 장점은 분명했습니다.

- 기존 개발자 워크플로우를 크게 바꾸지 않습니다.
- FDS 소스가 계속 단일 원천으로 유지됩니다.
- AI 활용을 위해 별도의 장기 유지 문서를 만들 필요가 없습니다.

즉 이 작업은 디자인 시스템 재구축이 아니라, 기존 자산의 접근 방식을 확장하는 일에 가까웠습니다.

## 왜 skill이 아니라 MCP였나

비슷한 질문을 자주 받습니다. "이걸 skill로 만들 수도 있지 않나?"

어느 정도는 가능하다고 생각합니다. 하지만 여기서 더 중요했던 것은 AI에게 어떤 설명을 주느냐보다, 현재 상태의 지식을 어떤 방식으로 공급하느냐였습니다.

skill은 정적인 가이드나 절차를 주는 데 강합니다. 반면 이 문제는 현재 FDS 코드, 현재 props, 현재 예제, 현재 토큰을 직접 조회할 수 있어야 했습니다. 디자인 시스템이 바뀌는 속도를 생각하면, 수동으로 유지되는 설명보다 실행 시점에 최신 정보를 읽는 구조가 더 적합한 것 같습니다.

그래서 이 문제에서는 skill보다 MCP가 더 적합했습니다. 둘 다 AI를 돕는다는 점은 같지만, 이 경우 필요한 것은 사용법을 설명하는 문서보다 최신 상태를 조회하는 인터페이스였기 때문입니다.

## 마치며

디자인 시스템이 있다고 해서 AI가 곧바로 그 시스템을 활용할 수 있는 것은 아닙니다. 사람에게는 당연한 연결이 AI에게는 빠져 있는 맥락일 수 있습니다. 그래서 실제 병목은 종종 코드 생성 능력보다, 사내 표준 지식을 얼마나 정확하게 연결하느냐에서 생기는 것 같습니다.

이번 작업의 목표는 새로운 FDS를 만드는 것이 아니었습니다. 이미 존재하는 FDS를 AI도 사용할 수 있는 자산으로 바꾸는 것이었습니다. 문서를 더 늘리는 대신, 코드와 예제와 토큰을 자동으로 읽어 MCP tool로 노출했습니다. 그 결과 사람의 설명에 의존하던 과정을, AI가 필요한 순간 직접 조회하는 구조로 바꿀 수 있었습니다.

앞으로 디자인 시스템의 사용자는 사람 개발자만이 아닐 가능성이 높습니다. AI도 같은 시스템을 사용하는 팀의 일원이라면, 중요한 것은 더 많은 설명을 쓰는 것이 아니라 기존 지식을 AI가 소비할 수 있는 방식으로 바꾸는 일인 것 같습니다.
