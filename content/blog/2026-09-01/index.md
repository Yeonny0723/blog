## "이거 안정적으로 운영될 수 있나?"

문서 생성 AI 에이전트 기능 개발이 거의 끝나갈 무렵, 팀장님이 물었다.

> "이거 안정적으로 운영될 수 있나? 서버 부하 될 만한 부분은 없어?"

바로 대답하지 못했다. 기능이 **돌아가는지**는 알았지만, 여러 사람이 동시에 쓸 때 **버티는지**는 생각해 본 적이 없었다.

그래서 직접 부하를 걸어 봤다. SSE 구독 인프라를 붙인 뒤 목업 클라이언트를 연결하고, 브라우저 탭을 여러 개 띄워 동시 구독을 계속 늘렸다. 구독 객체가 많아질수록 서버 부하가 실시간으로 올라가는 게 보였다.

이 글은 그 질문에 답하기 위해 다시 공부한 것과, 실제로 적용한 것을 정리한 기록이다.

**이 글이 다룰 것**
- 오래 걸리는 LLM 작업에서 진짜 병목은 무엇이었나
- 다시 공부한 동시성 개념: 스레드/프로세스, GIL, FastAPI의 실행 방식
- 파이프라인을 어떻게 재배치했나
- 동시 실행 수를 어떻게 정하고 어떻게 거절했나

## LLM이 느린 게 아니라, 기다리는 동안 쥐고 있는 게 문제였다

기존 코드는 전부 동기 방식이었다. LLM 클라이언트도 동기였다. 호출하면 응답이 올 때까지 그 스레드가 다른 일을 하지 못하고 기다렸다.

지금까지는 이게 문제로 드러나지 않았다. 대부분의 LLM 호출은 몇 초면 끝났기 때문이다. 잠깐 스레드를 붙잡았다가 금방 돌려줬다.

문서 생성 기능은 달랐다. 한 턴이 평균 5분, 길면 10분까지 걸린다. 그 안에 LLM 호출 단계도 여러 개다. 동기 클라이언트로 이걸 돌리면 한 턴이 5분 내내 스레드 하나를 물고 있게 된다.

- `def`로 돌리면 → 공용 스레드풀의 스레드를 5분씩 점유한다. 몇십 건만 겹쳐도 풀이 고갈된다.
- `async def` 안에서 동기 호출을 하면 → 더 나쁘다. 이벤트 루프 자체가 멈춰서 다른 모든 요청이 같이 멈춘다.

나는 처음에 "LLM 응답이 느린 것"이 문제라고 생각했다. 그런데 LLM 속도는 내가 바꿀 수 없다. 내가 바꿀 수 있는 건 **기다리는 동안 무엇을 쥐고 있느냐**였다.

솔직히 이 사실도 조사하면서 알게 됐다. "네트워크 I/O를 기다리는 동안 스레드가 계속 잡혀 있다"는 걸 머리로는 들어봤지만, 그게 5분짜리 작업에서 어떤 의미인지는 몰랐다. 그래서 기초부터 다시 정리했다.

## 다시 공부한 것들

### 코어, 스레드, 프로세스

| 개념 | 비유 | 설명 |
|---|---|---|
| 코어 | 작업자 | 실제로 명령을 실행하는 주체 |
| 스레드 | 작업 목록 | 실행할 명령 + 진행 상태 |
| 프로세스 | 작업 공간 | 메모리를 따로 가진 실행 공간. 안에 스레드가 여러 개 있을 수 있음 |

| | 멀티스레딩 | 멀티프로세싱 |
|---|---|---|
| 하는 일 | 한 프로세스 안에서 작업 흐름을 여러 개 만든다 | 실행 공간 자체를 여러 개 만든다 |
| 주로 쓰는 곳 | 네트워크 통신, 파일 입출력 (I/O 바운드) | 무거운 계산을 코어에 나눌 때 (CPU 바운드) |

### Java는 쉽고 Python은 다르다: GIL

Java에서 멀티스레딩은 직관적이다. 스레드가 각자 코어에 올라가서 정말로 동시에 실행된다.

```
Java 프로그램 (프로세스)
 ├─ 스레드 A ──▶ CPU 코어 1에서 실행
 ├─ 스레드 B ──▶ CPU 코어 2에서 실행
 └─ 스레드 C ──▶ 대기 또는 번갈아 실행
```

스레드 수가 코어 수보다 많으면 남는 스레드는 기다리거나 번갈아 실행된다.

Python도 멀티스레딩을 지원하지만 의미가 다르다. **GIL(Global Interpreter Lock)** 때문이다. GIL은 한 프로세스 안에서 한 번에 하나의 스레드만 Python 코드를 실행하게 하는 잠금장치다. 스레드를 여러 개 띄워도 계산은 사실상 한 줄로 선다.

그렇다고 Python 스레드가 쓸모없는 건 아니다. **I/O를 기다리는 동안에는 스레드가 GIL을 놓는다.** 그래서 LLM 응답 대기 같은 네트워크 I/O나 파일 I/O에는 스레드가 여전히 유효하다. 막히는 건 CPU 계산이 병목인 작업뿐이다.

(최근 Python 버전에서 GIL 없는 빌드가 선택지로 생겼지만, 기본 빌드에는 아직 GIL이 있다.)

### 그럼 Python은 실무에서 어떻게 동시에 처리하나

| 방식 | 도구 | 용도 |
|---|---|---|
| 워커 프로세스 여러 개 | `gunicorn --workers N` | 서버 자체를 여러 코어에 띄움 |
| 자식 프로세스 | `multiprocessing` | CPU 계산을 코어에 분산 |
| 미리 만든 풀에 맡기기 | `ThreadPoolExecutor`, `ProcessPoolExecutor` | 작업이 들어오면 빈 스레드·프로세스에 배정 |
| 싱글 스레드 + 이벤트 루프 | `asyncio` | 한 스레드에서 여러 I/O를 번갈아 진행 |

```
프로세스 (부모)
├─ ThreadPoolExecutor
│  ├─ 스레드 A ──▶ CPU 코어가 작업 실행
│  └─ 스레드 B ──▶ CPU 코어가 작업 실행
│
└─ ProcessPoolExecutor
   ├─ 자식 프로세스 A ── 스레드 ──▶ CPU 코어가 작업 실행
   └─ 자식 프로세스 B ── 스레드 ──▶ CPU 코어가 작업 실행
```

`asyncio`는 스레드를 늘리지 않는다. 한 스레드 안의 이벤트 루프가 "지금 진행할 수 있는 작업"을 골라 돌린다.

```
프로세스
└─ 스레드 A
   └─ 이벤트 루프: 실행할 비동기 작업을 골라 진행
      ├─ 요청 A: 네트워크 응답 대기 중 → 잠시 멈춤
      └─ 요청 B: 지금 실행 가능 → 이어서 실행
```

LLM 호출처럼 대부분의 시간을 "기다림"으로 보내는 작업에는 이 방식이 가장 잘 맞는다.

### FastAPI는 함수를 어디서 돌리나

| 정의 | 실행 위치 | 주의할 점 |
|---|---|---|
| `async def` | 이벤트 루프가 도는 메인 스레드 | 안에서 동기 블로킹 호출을 하면 루프 전체가 멈춘다 |
| `def` | 스레드풀 (anyio 기본 한도 40) | 오래 걸리면 공용 슬롯을 점유한다 |

Uvicorn에서는 메인 스레드의 이벤트 루프가 HTTP 요청, SSE 연결, 타이머를 모두 처리한다. `BackgroundTasks`도 같은 규칙을 따른다. `async def` 태스크는 이벤트 루프에서, `def` 태스크는 스레드풀에서 실행된다. 파일 읽기 같은 동기 작업은 `run_in_threadpool`로 다른 스레드에 넘겨야 루프를 막지 않는다.

정리하면 문서 생성 기능의 위험은 두 갈래였다.
1. 동기 LLM 호출을 `def`에서 하면 → 공용 스레드를 5분씩 점유
2. 동기 LLM 호출을 `async def`에서 하면 → 이벤트 루프 정지, SSE를 포함한 모든 응답이 멈춤

## 기다리는 단계는 await로, 계산하는 단계는 따로

문서 생성 한 턴은 크게 두 종류의 단계로 이루어진다.

| 단계 | 성격 | 실행 방식 |
|---|---|---|
| LLM 호출 단계 (여러 개) | 대부분의 시간을 응답 대기로 보낸다 (I/O 바운드) | 비동기 클라이언트 + `await` |
| 서버 내 검증 단계 | LLM 없이 서버에서 계산한다 | 별도 스레드풀 |

원칙은 단순하다. **기다리는 단계는 스레드를 놓고 기다리게 하고, 계산하는 단계만 스레드를 쓰게 한다.** LLM 클라이언트를 비동기로 바꾸고, LLM 없이 서버에서 하는 검증만 별도 스레드풀로 보냈다. Python 코루틴은 `await` 없이 부르면 실행되지 않기 때문에, 클라이언트만 바꿔서는 안 되고 호출부까지 `await`로 이어 줘야 했다.

구조만 보이도록 단순화한 예시는 다음과 같다(실제 코드가 아니다).

```python
from concurrent.futures import ThreadPoolExecutor
import asyncio

VERIFY_POOL = ThreadPoolExecutor(max_workers=N)  # LLM 없는 검증 전용

async def run_turn(req):
    result = req
    for step in LLM_STEPS:                 # LLM 호출 단계들
        result = await step(result)        # 기다리는 동안 루프는 다른 일을 한다

    loop = asyncio.get_running_loop()
    await loop.run_in_executor(VERIFY_POOL, verify, result)  # 계산은 루프 밖으로
```

이렇게 바꾸면 5분짜리 턴이 실제로 스레드를 쥐는 시간은 검증 단계뿐이다. 나머지 시간에는 이벤트 루프가 다른 요청과 SSE 이벤트를 처리할 수 있다.

**의도적으로 하지 않은 것**도 있다. 프로세스풀(`ProcessPoolExecutor`)은 쓰지 않았다. 이 기능에는 GIL이 문제가 될 만큼 무거운 CPU 연산이 없다. 이미지 리사이징이나 대량 데이터 가공처럼 계산이 병목인 작업이 들어오면 그때 별도 프로세스를 고려할 생각이다.

## 빈도가 아니라 점유를 제한한다

비동기로 바꿨다고 끝은 아니었다. 스레드는 덜 쓰게 됐지만, 턴 하나하나가 메모리와 SSE 연결을 5분씩 쥐고 있는 건 그대로다. 무제한으로 받으면 결국 어딘가가 터진다.

처음에는 rate limit을 떠올렸다. 그런데 rate limit은 **시간당 몇 번 요청하느냐**를 막는다. 상태 조회처럼 짧은 요청이 너무 자주 들어올 때 맞는 도구다.

| | rate limit | concurrency limit |
|---|---|---|
| 제한하는 것 | 단위 시간당 요청 **횟수** | 동시에 진행 중인 작업 **수** |
| 잘 맞는 경우 | 짧은 요청이 너무 자주 올 때 | 하나하나가 오래 걸릴 때 |
| 문서 생성에서 | 분당 1건이어도 5분이면 5건이 쌓인다 | 쌓이는 양 자체를 막는다 |

문서 생성 기능의 문제는 자주 오는 게 아니라 **오래 머무는 것**이었다. 그래서 rate limit은 넣지 않았다. 동시 실행 개수 제한만으로 부하를 충분히 제어할 수 있다고 판단했다.

카페로 비유하면 이렇다. 자리가 차는 건 손님이 자주 와서가 아니라 한 명 한 명이 오래 앉아 있어서다. 그러니 막아야 할 건 입장 횟수가 아니라 동시에 앉아 있는 사람 수다. 자리가 없으면 새 손님은 줄을 서는 대신 돌아간다.

> **오래 걸리는 작업에서 제한할 건 빈도가 아니라 점유다.**

### 상한을 거는 것과 몫을 떼어 두는 것은 다르다

공부하면서 헷갈렸던 게 하나 더 있다. "동시 실행 수 제한"과 "스레드풀 분리"는 비슷해 보이지만 막는 방향이 반대다. 공용 스레드가 10개 있다고 해 보자.

| | 동시 실행 수 제한 | 스레드풀 분리 |
|---|---|---|
| 예시 | 특정 기능은 최대 3개까지만 쓴다 | 특정 기능 전용으로 3개를 반드시 둔다 |
| 보장하는 것 | 그 기능이 공용을 **다 먹지 못하게** (최대 점유량 상한) | 다른 기능이 공용을 다 먹어도 **이 기능은 돌게** (최소 몫 보장) |

문서 생성 동시 실행 제한이 앞의 것이다. 검증 작업을 별도 풀로 뺀 건 뒤의 것이다. `def` 엔드포인트들이 공용 풀을 가득 채워도 검증 단계가 밀리지 않는다.

## 실행 한도 기준 잡기

한도를 걸기로 했으니 숫자가 필요했다. 감으로 정하지 않으려고 피크 상황을 가정했다.

```
동시 실행 수 ≈ 피크 시 분당 요청 수 × 평균 실행 시간(분)
```

큐잉 이론의 리틀의 법칙(L = λW)이다. 가령 분당 4건이 들어오고 한 건이 5분 걸리면, 어느 순간이든 약 20건이 동시에 돌고 있다. 여기에 여유를 더한 값을 동시 실행 한도로 잡았다.

| 항목 | 정한 기준 |
|---|---|
| 문서 생성 동시 실행 한도 | 피크 요청 수 × 평균 실행 시간 + 여유 |
| SSE 동시 구독 한도 | 동시 실행 한도보다 넉넉하게. 같은 사용자가 탭을 여러 개 열어 중복 구독할 수 있어서 |
| 적용 범위 | 워커별 |

그리고 이 값들은 코드에 박지 않고 **서버 설정으로 분리**했다. 고객사 환경마다 서버 사양이 다르니, 사양에 맞춰 적정값을 조정할 수 있어야 했다.

## 한도 초과 요청 처리

한도가 찼을 때 새 요청을 어떻게 할지도 정해야 했다. 선택지는 셋이었다.

| 선택지 | 장점 | 문제 |
|---|---|---|
| 외부 큐(메시지 브로커) | 대기열을 안전하게 보관 | 고객사 환경에 별도 서비스를 하나 더 깔아야 함. 지금 규모에는 과함 |
| 인메모리 대기열 | 추가 인프라 없음 | 크기를 정하지 않으면 OOM 위험. 크기를 정해도 5분짜리 작업을 대기열에서 또 기다리게 됨 |
| **즉시 503 거절** | 서버가 감당할 양만 받음 | 사용자가 다시 시도해야 함 |

서비스 규모가 크지 않고, 서버 스펙이 넉넉하지 않을 수도 있는 환경이라 외부 큐는 과했다. 인메모리 대기열은 크기를 정해 두면 메모리 문제는 막을 수 있다. 하지만 실행에만 5분이 걸리는 작업을 대기열에서 또 기다리게 하면, 사용자 입장에서는 사실상 실패와 같다고 판단했다. 언제 시작될지도 모르는 채로 기다리게 하느니, 지금은 받을 수 없다고 바로 알려 주는 편이 낫다.

그래서 대기열을 만들지 않고, 한도가 차면 **새 요청을 즉시 503(Service Unavailable)으로 거절**하기로 했다. 특정 클라이언트가 너무 자주 요청한 게 아니라 서버 전체 수용량이 찬 상황이라 429가 아닌 503을 썼다. 흔히 load shedding이라고 부르는 방식이다.

거절 로직 자체는 간단하다. 아래도 구조를 보여 주기 위한 예시다.

```python
LIMIT = settings.concurrency_limit  # 서버 설정값
running = 0

@app.post("/turns")
async def start_turn(req: TurnRequest):
    global running
    if running >= LIMIT:
        raise HTTPException(status_code=503, detail="잠시 후 다시 시도해 주세요.")
    running += 1
    asyncio.create_task(run_turn_and_release(req))  # 끝나면 finally에서 running -= 1
    return {"status": "accepted"}
```

이벤트 루프는 한 스레드에서 돌기 때문에, 확인과 증가 사이에 `await`가 없으면 별도 락 없이도 카운터가 꼬이지 않는다.

**감수한 것**도 분명하다.
- 덜 쓰는 것: 외부 큐 인프라, 대기 요청이 차지할 메모리
- 더 쓰는 것: 사용자의 수고. 503을 받으면 프론트엔드가 안내 메시지를 띄우고, 사용자가 잠시 기다렸다가 **직접 다시 눌러야** 한다

### 이벤트도 쌓아 두지 않는다

같은 원칙을 SSE 이벤트에도 적용했다. 구독마다 쌓아 둘 수 있는 이벤트 수에 상한을 두고, 넘치면 **가장 먼저 들어온 이벤트부터 버린다.**

버려도 되는 이유는 이 이벤트의 성격에 있다. DB에 저장하는 데이터가 아니라, 작업이 지금 어디까지 진행됐는지 보여 주는 일회성 메시지다. 사용자에게 필요한 건 최신 상태이고, 지나간 진행 메시지는 금방 의미를 잃는다. 그러니 오래된 것을 붙잡고 있을 이유가 없다. 상한은 작게 잡아도 충분하다.

## 워커가 여러 개면 생기는 일

워커를 여러 개 띄우면서 문제가 하나 더 생겼다. 구독 객체와 발행할 이벤트가 각 워커의 메모리에 있다. 그런데 **구독을 만든 워커와 이벤트를 발행하는 워커가 다를 수 있다.** A 워커에 연결된 사용자에게 B 워커가 만든 이벤트를 전달할 방법이 필요했다.

그래서 Redis를 붙였다. 구독 목록과 이벤트 큐는 여전히 각 워커가 자기 메모리에서 관리한다. Redis는 들어온 요청이나 이벤트를 필요한 워커로 **라우팅하는 역할만** 맡는다.

- 한도를 넘는 요청은 503으로 거절되는 것을 직접 확인했다.
- 그동안 다른 API 응답이 크게 느려지지 않는 것도 확인했다.
