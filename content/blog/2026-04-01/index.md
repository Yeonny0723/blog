얼마나 빠르게 개발하느냐에 더불어서, 제품적인 특성으로도

# npm 공급망 공격과 Axios 2026 사례

## 1. 사건 요약

2026년 3월 31일, Axios의 유지보수자 계정이 침해되면서 npm 레지스트리에 **악성 버전 `axios@1.14.1`, `axios@0.30.4`** 가 게시되었습니다. 두 버전은 `plain-crypto-js@4.2.1`이라는 악성 의존성을 추가했고, 이 의존성은 설치 시점의 스크립트를 통해 macOS, Windows, Linux용 2차 RAT(원격 제어 악성코드)를 내려받도록 설계됐습니다. Axios 공식 사후 보고서에 따르면 해당 버전은 약 3시간 동안 게시되어 있었으며, 설치한 머신은 **침해된 것으로 간주**해야 한다고 안내하고 있습니다.

핵심은, 애플리케이션 코드가 실행될 때가 아니라 **`npm install` 자체가 공격 진입점**이 될 수 있다는 점입니다. 공격자는 Axios의 런타임 로직을 크게 바꾸지 않고, 설치 과정에서만 동작하는 악성 의존성을 넣어 정상 동작처럼 보이게 만들었습니다.

## 2. npm 공급망 공격이란?

**npm 공급망 공격(supply chain attack)**
은 우리 저장소를 직접 해킹하는 대신, 우리가 신뢰하고 받아 쓰는 **패키지·의존성·배포 경로**를 공격하는 방식입니다.

개발자는 보통 직접 추가한 패키지만 봅니다.

예를 들어:

```json
{
  "dependencies": {
    "my-sdk": "^2.0.0"
  }
}
```

하지만 실제 설치는 이런 트리가 될 수 있습니다.

- `my-sdk`
  - `axios`
    - `plain-crypto-js` ← 악성 의존성

`npm install`로 axios 코드를 받아오게되면, `plain-crypto-js`를 직접 설치하지 않았더라도 내가 신뢰한 공식 패키지가 설치되는 시점 악성 의존성을 끌고와 감염될 수 있습니다. npm은 논리적 의존성 트리를 바탕으로 하위 패키지까지 전부 설치하게 됩니다.

## 3. 공격의 방식은?

Axios 사건 단순화 흐름:

1. 공격자가 유지보수자 계정 또는 배포 권한을 탈취합니다.
2. 공식 패키지의 새 버전에 악성 의존성을 추가합니다.
3. 개발자 PC나 CI가 `npm install`, `npm update`, 혹은 새 환경 셋업을 수행합니다.
4. 패키지 매니저가 설치 도중 패키지의 라이프사이클 스크립트를 자동 실행합니다.
5. 이 스크립트가 2차 악성코드를 내려받거나 실행합니다.
6. 이후 토큰 탈취, 원격 제어, 추가 백도어 설치, CI 비밀 유출로 이어질 수 있습니다.

> 4단계에서 공격자는 애플리케이션 런타임 로직을 크게 바꾸지 않고도, 외부 패키지 쪽 설치 스크립트만으로 코드 실행 지점을 만들 수 있습니다.

npm 공식 문서에 따르면 `npm install`과 `npm ci`에서 다음 스크립트들이 순서대로 실행될 수 있습니다.

- `preinstall`: 설치 관련 작업 전에 실행
- `install`: 설치 단계에서 실행
- `postinstall`: 설치가 끝난 직후 실행

공급망 공격 맥락에서 특히 주목해야 할 것은 `preinstall`, `install`, `postinstall`입니다. 이 셋은 설치되는 패키지나 하위 의존성에 들어 있을 때 소비자 환경의 `npm install` 과정에서 직접 실행 지점이 되기 쉽습니다.

실무적으로는 공격자가 가장 많이 악용하는 지점이 `postinstall`입니다. 설치가 끝난 직후 추가 파일 다운로드나 실행을 숨기기 쉽기 때문입니다.

## 4. 취약한 환경

1. lockfile 없이 새로 설치하는 경우 <br>
   `package-lock.json`이나 `yarn.lock`이 없거나, 있어도 무시하고 설치하면 그 시점의 최신 버전을 새로 해석하게 됩니다.

2. semver 범위를 느슨하게 쓰는 경우 <br>
   `^1.14.0`, `~1.14.0`, `*` 같은 범위를 넓게 열어두면, 패키지 게시 직후 의도치 않은 버전을 받을 수 있습니다.

3. 개발자 로컬 머신이 회사 비밀과 연결된 경우

- 회사 Git 접근권
- SSH 키
- 클라우드 CLI 로그인
- 브라우저 저장 자격증명
- 사내 VPN/SSO 세션
  공격자는 이 환경을 통해 조직 내부로 더 깊게 들어갈 수 있습니다.

4.  CI/CD 전체가 오염될 수 있습니다
    로컬 PC 문제에서 그치지 않고 빌드 파이프라인, 릴리스 체인, 내부 패키지 발행 체인까지 연결될 수 있습니다.

# 플러그인 설계: npm-supply-chain-guard

(현재 문서에서 `npm audit`, `yarn audit`는 같은 역할을 합니다. 편의상 `npm`을 기준으로 기재합니다.)

위에서 살펴본 위협들에 팀이 빠르게 가드레일을 두기 위해 Claude Code 플러그인을 설계했습니다. 핵심 컨셉은 다음과 같습니다.

```
install은 일반 명령이 아닌 보안 민감 작업으로 간주한다.
```

`install` 시점을 가장 큰 진입점으로 보고, 그 앞뒤를 3개의 명령과 1개의 훅으로 감쌌습니다.

- `/init`: 설치 전 환경 자체를 안전하게 (설정 파일)
- `/audit`: 현재 상태 점검 + 안전한 자동 수정
- `/git:commit`: 의존성 변경 시점 가드
- PreToolUse 훅: install 명령 실시간 가드

각 단계가 어떤 위협 지점을 막는지 풀어보겠습니다.

## 1. `/init` — 프로젝트 보안 설정 초기화

프로젝트 루트에 `.npmrc`와 `.yarnrc.yml`의 보안 설정을 추가하는 명령입니다. 패키지 매니저별로 보안에 영향을 주는 기본값을 코드 외부에서 강제하는 것이 목적입니다.

`.npmrc`에는 다음 키를 적용합니다.

```ini
ignore-scripts=true
save-exact=true
audit=true
audit-level=high
package-lock=true
```

각 키의 의미는 이렇습니다.

- `ignore-scripts=true`: `preinstall` / `install` / `postinstall` 같은 라이프사이클 스크립트를 기본 비활성화합니다. 앞에서 공급망 공격의 주요 실행 지점으로 다룬 그 스크립트들을 차단하는 가장 직접적인 방어선입니다.
- `save-exact=true`: 새 패키지를 추가할 때 `^`, `~` 없이 정확한 버전으로 저장합니다. semver 범위를 넓게 열어두면 게시 직후의 악성 버전을 받을 수 있기 때문입니다.
- `audit=true`, `audit-level=high`: install 시 자동으로 감사를 실행하고, high 이상 취약점에서 실패하도록 합니다.
- `package-lock=true`: lockfile 생성을 강제합니다.

Yarn 프로젝트라면 `.yarnrc.yml`에 `enableScripts: false`, `enableImmutableInstalls: true`, `checksumBehavior: throw`를 적용해 같은 방어선을 만듭니다.

이미 파일이 있는 경우에는 누락된 키만 추가하고, 충돌하는 값이 있으면 덮어쓰지 않고 경고만 출력합니다. 기존 팀 정책을 망가뜨리지 않으면서 보안 기본값만 위로 끌어올리는 게 의도입니다.

## 2. `/audit` — 의존성 위험 감사

가장 핵심이 되는 명령입니다. `npm audit`만으로는 부족했던 부분들을 한 흐름으로 묶어, lockfile · semver · 의존성 트리 · 운영 체크리스트까지 함께 점검합니다.

먼저 `npm audit` 자체부터 짚고 가야 합니다. `npm audit`은 **현재 프로젝트 의존성에 알려진 취약점이 있는지 npm 레지스트리에 질의해서 보고서를 받는 명령**입니다. npm 공식 문서에 따르면, audit는 프로젝트에 구성된 의존성 정보를 기본 레지스트리에 제출하고, 알려진 취약점과 그 영향도, 가능한 수정 방법을 계산해 줍니다.

```bash
npm audit
npm audit fix
```

다만 `npm audit`은 **이미 알려진 취약점 데이터베이스 기반**으로 동작합니다. 따라서 다음과 같은 경우에는 한계가 있습니다.

- 막 올라온 악성 릴리스
- 아직 CVE나 advisory가 정리되지 않은 공급망 공격
- 설치 시점에만 동작하는 교묘한 악성 코드

즉, `npm audit`는 필요하지만 **충분하지는 않습니다**. Axios 같은 사고에서 초기 몇 시간은 audit만으로는 놓칠 수 있습니다. 그래서 `/audit` 명령은 `npm audit`을 8단계 흐름의 한 부분으로만 사용하고, 나머지 단계가 audit이 놓치는 영역을 보완하도록 구성했습니다.

전체 흐름은 다음과 같습니다.

1. **패키지 매니저 자동 감지** — lockfile 종류로 npm/yarn을 식별합니다. lockfile이 하나도 없으면 감사를 중단합니다. lockfile 부재 자체가 가장 큰 위험이기 때문입니다.
2. **lockfile git 추적 여부 확인** — `git ls-files`, `git check-ignore`로 lockfile이 git에 누락되어 있지 않은지 확인합니다. lockfile이 .gitignore에 들어가 있으면 사실상 없는 것과 같습니다.
3. **`npm audit --json` 실행** — Critical / High / Moderate / Low로 분류해 출력합니다. Critical 항목은 CVE 번호, 수정 버전, 의존성 경로, advisory URL까지 상세하게 풀어 보여주도록 했습니다. 의존성 경로가 있어야 "어떤 직접 의존성을 통해 들어왔는지"를 빠르게 추적할 수 있어서요.
4. **loose semver 범위 검사** — `package.json`의 모든 의존성 필드(`dependencies`, `devDependencies`, `peerDependencies`, `resolutions`, `overrides` 등)에서 `^`, `~`, `*`, `.x`를 추출합니다. `file:`, `github:`, `workspace:` 같은 프로토콜은 false positive로 제외합니다.
5. **의존성 트리 출력 (depth 3)** — `npm ls --depth=3`으로 직접 의존성 너머의 트리도 함께 노출합니다. Axios 사례에서도 문제가 된 건 직접 추가한 패키지가 아니라 그 아래에 끌려들어온 `plain-crypto-js`였습니다.
6. **수동 점검 체크리스트 출력** — 도구가 자동으로 판단할 수 없는 영역(빌드에 꼭 필요한 secret만 주입했는지, 토큰 scope 최소화, publish용 토큰과 runtime 토큰 분리, OIDC 기반 publish 설정, 자동 머지 최소화 등)을 체크리스트 형태로 출력합니다.
7. **safe fix 자동 적용** — 취약점이 1개 이상 발견된 경우에만 실행됩니다. `npm audit fix --dry-run --json`으로 변경 범위를 먼저 파악한 후, patch/minor 범위만 자동 실행합니다. major 변경이나 `--force`가 필요한 변경은 자동 실행하지 않고 경고만 출력합니다. yarn 프로젝트는 `npm audit fix`를 지원하지 않기 때문에 자동 수정 대신 `yarn upgrade <패키지>@<수정버전>` 가이드 메시지로 폴백합니다.

특히 마지막 safe fix 단계는 `npm audit fix --force`를 절대 자동 실행하지 않도록 설계했습니다. force는 breaking change를 동반할 수 있어서, 자동화하면 보안 문제를 막으려다 운영 사고를 만들 수 있기 때문입니다. patch/minor는 사람의 판단 없이도 안전한 편이라 자동으로, 그 이상은 사람이 판단하도록 분기했습니다.

## 3. `/git:commit` — 커밋 시 의존성 변경 가드

의존성 변경 커밋은 코드 변경 커밋과 **다른 리뷰 흐름**이 필요하다는 전제로 만든 명령입니다. 사고가 났을 때 lockfile 변경이 다른 코드 변경과 한 커밋에 섞여 있으면 추적이 어려워집니다.

스테이지된 파일 중 `package.json`이나 lockfile이 포함되면 다음을 수행합니다.

- semver 범위 검사 (`^`, `~`, `*`, `.x` 패턴 추출 → 정확한 버전 고정 권장)
- 코드 변경과 lockfile 변경을 **별도 커밋으로 분리**할 것을 권장
- `package.json`만 변경되었고 lockfile이 빠져 있는 경우 명시적으로 안내

그리고 `/git:commit`은 메시지를 바로 만들지 않고, **커밋 계획(분할 여부 · 메시지 · 스테이징 목록)을 먼저 사용자에게 제시하고 승인을 받은 뒤 실행**합니다. 모든 커밋에 적용되는 일반 동작이지만, 의존성 변경 커밋에서 특히 가치를 발휘합니다. 자동 커밋의 빠르기보다 한 번 더 보는 안전함을 택한 셈입니다.

## 4. PreToolUse Bash 훅 — install 명령 실시간 가드

명령 4개와 별개로, Claude Code가 Bash 도구로 install 명령을 실행하려고 할 때 **실시간으로 가로채는** 훅을 추가했습니다. 사용자가 `/audit`이나 `/init`을 부르는 걸 잊더라도, 위험한 install 자체가 그냥 통과되지 않도록 하는 장치입니다.

훅의 기본 컨셉은 `npm ci --ignore-scripts`로 install을 표준화하는 것입니다. 이 명령이 왜 권장 기본값인지 한 번 짚고 가겠습니다.

`npm ci`는 **CI/CD나 자동화 환경에서, lockfile 기준으로 깨끗하고 재현 가능한 설치를 하기 위한 명령**입니다.

- `package.json`과 lockfile이 맞지 않으면 lockfile을 고치지 않고 **에러로 종료**합니다.
- `package.json`이나 lockfile을 수정하지 않습니다. 즉, **설치 결과가 frozen**에 가깝습니다.
- CI와 로컬의 의존성 차이를 줄여줍니다.
- 사고 발생 시 "문제 버전이 lockfile에 들어 있었는가?"를 더 정확히 추적할 수 있습니다.

여기에 의도하지 않은 설치 스크립트 실행을 최소화하기 위해 `--ignore-scripts`를 함께 사용합니다.

```bash
npm ci --ignore-scripts
```

훅은 이 컨셉을 기준으로 install 명령을 분기 처리합니다.

| 명령                                                                                      | 동작                                               |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `npm ci --ignore-scripts` / `yarn install --immutable` / `yarn install --frozen-lockfile` | 통과 (안전 패턴)                                   |
| lockfile 없는 install                                                                     | **차단 (exit 2)**                                  |
| `npm install` / `npm update`                                                              | `npm ci --ignore-scripts` 사용 권장 경고           |
| `--ignore-scripts` 없는 `npm ci`                                                          | `--ignore-scripts` 추가 권장 경고                  |
| `yarn add`                                                                                | 새 의존성 추가 시 출처 확인 · audit 실행 권장 경고 |
| `yarn install`                                                                            | `--immutable --ignore-scripts` 사용 권장 경고      |

가장 중요한 분기는 **lockfile이 없으면 install을 차단**하는 부분입니다. lockfile 없이 install하면 패키지 매니저가 semver 범위 내 최신 버전을 새로 해석하기 때문에, Axios 2026 같은 사고가 발생한 시점에 install을 하면 그대로 악성 버전을 받게 됩니다. 일부 패키지는 정상 동작에 설치 스크립트가 필요할 수 있어, `--ignore-scripts`는 차단이 아닌 경고로만 권장합니다. 팀 정책과 호환성을 함께 검토해 결정하면 됩니다.
