최근 몇 달 사이 제 업무 범위가 프론트엔드에서 AI 서버 개발·운영, 백엔드까지 빠르게 넓어졌습니다. AI와 함께 짧은 시간에 많은 코드를 처리하며 속도는 분명히 빨라졌는데, 어느 순간 이상한 공백이 생겼습니다. AI가 만든 작업물과 그것을 대하는 제 이해 사이에 틈이 벌어진 겁니다. 코드는 동작하는데, 왜 이런 형태인지를 제가 설명하지 못하는 구간이 늘었습니다.

그 틈이 선명하게 드러난 건 팀원의 질문 앞에서였습니다. "이건 왜 이 방법으로 하신 거예요?"라는 물음에 답하려는데, 그 결정은 며칠 전 Claude와의 세션 어딘가에서 내려진 것이었고, 저는 그 세션을 resume해서 되짚어볼 수조차 없었습니다. 더 당황스러운 건 저 자신이었습니다. 오전에 고치던 이슈로 오후에 돌아오면, 그때 제가 왜 그렇게 판단했는지가 잘 기억나지 않는 순간이 잦아졌습니다.

결국 특정 시점부터 제 맥락도, 팀원의 맥락도 추적이 되지 않았습니다. 이 글은 그 문제를 어떻게 진단했고, "팀원과 맥락을 공유하기 어려워진 상황"을 Git 워크플로우 설계로 어떻게 풀어봤는지 정리한 기록입니다. AI를 적극적으로 쓰는 팀에서 비슷한 공백을 느끼는 분이라면, 바로 적용해볼 만한 몇 가지 기록 패턴을 얻어가실 수 있습니다.

## 업무가 넓어지자 맥락이 가장 먼저 무너졌습니다

역할이 늘어난다는 건 단순히 할 일이 많아진다는 뜻이 아니었습니다. 프론트엔드만 보던 때는 코드 리뷰에서 오간 이야기, 회의에서 나온 결정 하나하나를 자연스럽게 기억할 수 있었습니다. 도메인이 하나였고, 팀도 그 안에서 비슷한 속도로 움직였기 때문입니다.

지금은 같은 날 프론트엔드 이슈를 보다가 AI 파이프라인 이슈로 넘어가고, 백엔드 API 이슈까지 처리합니다. 각 영역은 판단 기준도, 관련된 사람도 다릅니다. 그러다 보니 "왜 이 방식을 선택했는지"에 대한 기억이 도메인 사이를 옮겨 다니는 과정에서 계속 휘발됐습니다.

예전에는 이 맥락이 팀 안에서 자연스럽게 나뉘어 저장됐습니다. 네이버의 하용호님이 "AI 시대 나의 전문성을 재설계하는 법" 세션에서 짚었듯, 여러 명이 회의에서 논의하고 코드 리뷰에서 의견을 주고받는 과정 자체가 맥락을 각자의 머릿속에 복제하는 절차였습니다. 이 대목이 특히 와닿았던 건, 제 상황이 정확히 그 복제 과정이 생략된 상태였기 때문입니다. 작업 속도가 천정부지로 오르면서 그 절차가 사라졌고, 나 자신의 맥락조차 흔들리는데 다른 사람이 내가 짠 코드를 보고 의도를 재구성하는 일은 훨씬 더 어려울 수밖에 없었습니다.

## AI 시대의 의도 부채

이 현상에는 이미 이름이 붙어 있었습니다. 같은 세션에서 하용호님은 이렇게 쌓이는 것을 기술 부채와 구분해 의도 부채라고 불렀습니다. 제가 겪던 공백이 단순히 바빠서 생긴 게 아니라 AI와 함께 일하는 방식 자체가 만드는 부채라는 걸, 그 이름 덕분에 또렷하게 정리할 수 있었습니다.

그 세션의 설명을 빌리면, AI가 만든 코드는 대체로 당장의 목적 달성에만 집중합니다. 때로는 기존 코드와 중복되고, 때로는 정공법 대신 우회로를 택합니다. 코드 자체는 동작하지만 "왜 이런 형태여야 했는지"에 대한 설명은 코드에 남지 않습니다. AI는 생각(thinking)을 대신 해줄 수는 있어도, 그 생각의 배경을 이해(understanding)하는 일까지 대신해주지는 않습니다.

코드는 멀쩡한데, 그것이 왜 그 형태인지, 어떤 제약과 트레이드오프 위에서 결정됐는지를 설명할 사람이 아무도 남지 않는 상태. 이게 의도 부채입니다. 제게 이 개념이 특히 와닿았던 건, 팀원의 "왜 이렇게 하셨어요?"에 제가 답하지 못한 순간이 바로 그 부채가 청구되는 장면이었기 때문입니다.

## 그래서 질문을 바꿨습니다

의도 부채라는 프레임을 잡고 나니, 스스로에게 묻는 질문도 바뀌었습니다. "이 코드가 동작하는가"가 아니라 "이 계획은 내 암묵지를 잘 반영하고 있는가", "내가 설명을 충분히 하지 않아서 결과물이 제멋대로 나올 위험은 없는가"를 먼저 확인해야 했습니다.

역할을 다시 놓고 보라는 것도 같은 세션에서 얻은 관점이었습니다. 저는 코드를 직접 치는 작성자라기보다 결과를 검증하고 방향을 잡는 검증자이자 조언자에 가까워졌고, 그렇다면 AI는 제 암묵지를 집요하게 캐묻는 적극적인 질문자여야 했습니다. 그 세션에서 실마리로 소개된 것이 matt-pocock의 `/grill-with-docs` 방식이었습니다. 계획의 모든 갈래를 따라가며 같은 이해에 도달할 때까지 집요하게 질문하게 하는 방식인데, 이게 알려준 건 하나였습니다. 맥락 공유는 저절로 되지 않고, 확정해야 할 지점을 의도적으로 만들어야 남는다는 것입니다.

그래서 워크플로우에 결정 게이트를 뒀습니다. 구현 도중 계획에 없던 결정 지점을 만나면 임의로 정하지 않고, 멈춰서 선택지와 트레이드오프를 정리해 확인을 받습니다. 그리고 그 결정이

- 되돌리기 어렵고
- 맥락 없이 나중에 보면 의아하고
- 실제 트레이드오프의 결과라면

그 경위를 반드시 기록으로 남깁니다. 이 세 조건에 걸리는 결정을 조용히 흘려보내면, 그게 곧 다음 의도 부채가 됐습니다.

## Git을 맥락 보존 장치로 다시 설계했습니다

이제 확정한 맥락을 구조적으로 붙잡아 둘 장치가 필요했습니다. 답은 이미 쓰던 Git이었습니다. 그동안 이슈와 MR을 "작업 티켓"과 "코드 diff"로만 써 왔는데, 이걸 "맥락을 재구성할 수 있는 기록"으로 바꾸기로 했습니다.

그래서 두 가지를 원칙으로 세웠습니다.

```
1. 모든 이슈의 배경과 의사결정을 기록한다.
2. 팀원 모두가 같은 배경을 공유하게 한다.
```

기준은 단순합니다. 나중에 합류한 팀원이 이슈 → plan 문서 → MR 순서로만 따라가도 "왜 이렇게 만들었는지"를 재구성할 수 있어야 한다는 것입니다.

이걸 지키려면, 작업을 맡을 때마다 무작정 시작하지 않고 규모부터 판정해야 했습니다. 규모에 따라 기록해야 할 맥락의 종류와 Git 구조가 다르기 때문입니다.

| 규모 | 기준                      | Git 구조                       |
| ---- | ------------------------- | ------------------------------ |
| 소형 | 버그 수정, 한두 파일 수정 | 이슈 1 + MR 1                  |
| 중형 | 단일 기능, MR 1개로 완결  | 이슈 1 + 체크리스트 + MR 1     |
| 대형 | 에픽 규모, 여러 화면·모듈 | 부모 이슈 + 하위 이슈 N + MR N |

소형은 원인을 규명한 과정이, 중형은 단일 기능을 두고 내린 설계 결정이, 대형은 여기에 더해 하위 작업 사이의 공유 계약과 병합 순서가 맥락이 됩니다.

그래서 규모별로 밟는 체인을 정해두고, 각 단계에서 맥락이 이슈·plan·MR 중 한 곳에 떨어지도록 배치했습니다.

**소형**은 가장 짧습니다. 원인을 규명하는 과정이 이슈 코멘트로 남는 게 핵심입니다.

```
1. 이슈 생성 (버그 템플릿, Root Cause는 "가설")        → /git:issue
2. systematic-debugging — 조사 경과·중간 가설을 코멘트로  → /git:comment
3. 원인 확정 시 이슈 본문 Root Cause를 "확정"으로 갱신
4. test-driven-development (재현 테스트 → 수정)
5. verification-before-completion
6. MR 생성 (Closes #N)                                → /git:pr
```

**중형**은 앞에 설계 단계가 붙습니다. 미결정 사항을 먼저 확정해 plan에 반영하고, 결정 경위는 MR Decisions에 남깁니다.

```
1. brainstorming (요구사항·설계 탐색)
2. /grill-with-docs (미결정 사항을 사용자 결정으로 확정)
3. writing-plans (plan 문서 → docs/plans/ 커밋)
4. 이슈 생성 (요약 + plan 링크 + 단계를 체크리스트로)     → /git:issue
5. executing-plans (단계별 실행, TDD 적용)
6. requesting-code-review + ponytail-review (오버엔지니어링 점검)
7. MR 생성 (Closes #N)                                → /git:pr
```

**대형**은 부모 이슈 아래로 쪼개, 하위 이슈를 worktree에서 격리해 병렬로 굴립니다.

```
1. brainstorming (전체 범위 1회)
2. /grill-with-docs (아키텍처·경계·하위 이슈 간 인터페이스 확정)
3. writing-plans (전체 plan 1개, MR 경계로 섹션 분할)
4. 부모 이슈 + 섹션당 하위 이슈 생성                     → /git:issue
5. 하위 이슈별: worktree 격리 → 실행 → 리뷰 → MR (타깃=부모 브랜치)
6. 소모품 docs 제거 → 부모 브랜치 → 개발 통합 브랜치 MR   → /git:pr
```

각 규모에서 맥락을 실제로 붙잡는 장치는 조금씩 다릅니다.

## 증상부터 남기고, 원인은 가설로 추적했습니다

위 소형 체인에서 맥락을 지키는 건 1~3단계입니다. 버그 수정에서 가장 중요한 맥락은 "원인을 찾아간 과정"인데, 이 과정은 원인이 확정되는 순간 가장 쉽게 지워지기 때문입니다. 그래서 버그 이슈 템플릿의 Root Cause를 상태 필드로 두고, 가설에서 시작하게 했습니다.

```
## Root Cause

**상태**: 가설   <!-- 가설 | 확정 -->
```

이슈는 디버깅을 시작하기 전에 만들기 때문에, 제목도 원인이 아니라 증상으로 답니다.

```
자정 이후 과거 날짜 로그 파일에 로그가 계속 쌓임
```

원인이 확정되면 상태를 "확정"으로 바꿉니다. 덕분에 나중에 비슷한 증상이 다시 올라와도, 한 번 기각한 가설을 처음부터 다시 밟지 않아도 됩니다.

## 무엇을 어디에 기록할지부터 정했습니다

기록을 남기라는 원칙만으로는 부족했습니다. 막상 맥락을 남기려 하면 "이걸 어디에 써야 하지?"에서 매번 멈칫하게 되고, 그 망설임이 결국 아무 데도 남기지 않는 결과로 이어졌기 때문입니다. 그래서 기록의 종류마다 위치를 못 박았습니다.

- **원인 규명 경과**는 이슈 코멘트에 남깁니다. 시간순으로 쌓이는 조사 로그에 적합합니다.
- **설계 결정**은 내용과 경위(검토한 대안, 선택 이유)를 함께 MR 본문의 Decisions 섹션에 남깁니다. 결정 기록의 정본은 별도 문서가 아니라 이곳입니다.
- **plan 문서**는 `docs/plans/`에 커밋하되 소모품으로 취급합니다. 세션과 worktree를 넘나드는 동안의 실행 기준일 뿐, 머지 후에는 갱신 의무가 없는 당시 스냅샷입니다.

다만 Decisions는 만들어 두는 것보다 어떻게 쓰느냐가 중요했습니다. 결론만 한 줄 적으면 그 상황을 겪지 않은 리뷰어에게는 정보가 되지 못하기 때문입니다. 그래서 템플릿에 작성 순서를 아예 박아뒀습니다.

```
### 1. <결정 제목>

**배경.**   무엇이 어떻게 동작하길래 문제가 되는지
**문제.**   안 고치면 어떤 입력에 어떤 잘못된 결과가 나오는지

- 검토한 대안 — (a) … : 기각 이유. (b) … : 기각 이유.
- 선택 — … (대가: 무엇을 포기했는지)
```

"smart-union이 값을 조용히 해석하도록 두었다" 같은 결론이 아니라, 왜 그런 일이 벌어지고 무엇이 깨지는지를 배경부터 쓰게 하는 장치입니다. 이 순서만으로도 같은 결정이 남기는 기록의 밀도가 달라졌습니다.

한 가지 더 지킨 원칙은, 이슈를 자체 완결적으로 쓴다는 것이었습니다. plan과 spec은 소모품이고, 나중에 합류한 팀원은 애초에 그 레포에 접근하지 못할 수도 있습니다. 그래서 이슈만 읽고도 "무엇을, 왜, 어디까지" 만들지 이해되도록 목표와 범위, 완료 기준을 본문에 담았습니다. plan 경로는 내용을 대체하는 링크가 아니라 보충 자료로만 곁들였습니다.

## 여러 MR이 얽히면 브랜치 토폴로지로 풀었습니다

대형 작업에서는 맥락이 하나 더 늘어납니다. 여러 하위 작업이 동시에 진행되기 때문에, 그들 사이의 공유 계약(스키마, 인터페이스)과 병합 순서 자체가 반드시 보존해야 할 맥락이 됩니다.

이걸 브랜치 구조로 풀었습니다. 하위 이슈 브랜치는 개발 통합 브랜치로 직접 보내지 않고, 부모 이슈의 작업 브랜치에서 분기해 다시 그 부모 브랜치로 병합합니다.

```
development
   └── feat/42-mobile (부모 작업 브랜치)
         ├── feat/43-dashboard (하위) ──┐
         ├── feat/44-profile   (하위) ──┤→ 부모 브랜치로 병합
         └── feat/45-settings  (하위) ──┘
```

이 구조를 택한 데는 두 가지 이유가 있었습니다.

첫째, 하위 이슈들이 공유하는 계약이 부모 브랜치에 먼저 모여야, 뒤따르는 하위 작업이 그 계약을 소비할 수 있습니다. 공유 스키마를 만드는 하위 이슈를 먼저 부모 브랜치에 머지한 뒤, 그다음 하위 브랜치를 부모에서 새로 분기하면 그 산출물을 그대로 확보할 수 있습니다.

둘째, 소모품인 plan과 spec이 부모 브랜치에만 머물러 개발 통합 브랜치로 새지 않습니다. 최종적으로 부모 브랜치를 개발 통합 브랜치로 병합하기 직전에 소모품 문서를 정리해 제거하면, 통합 브랜치는 깨끗하게 유지됩니다.

다만 브랜치를 나눠도 이슈 목록에서 계층이 안 보이면 소용없습니다. 제가 쓰는 GitLab CE에는 네이티브 epic이 없어, 목록만 봐서는 어떤 이슈가 어디에 속하는지 드러나지 않았습니다. 그래서 계층을 제목과 라벨로 드러냈습니다. 하위 이슈 제목엔 `(상위 이슈 #42)` 접미사를, 부모 이슈엔 `epic` 라벨을 답니다. 리뷰어가 목록만 훑어도 이 MR이 어느 작업의 일부인지 보이고, 그 전체 맥락까지 끌어와 읽을 수 있습니다.

## 부채가 될 코드는 애초에 덜 만들었습니다

지금까지가 이미 내려진 결정을 기록하는 이야기였다면, 그 앞단도 있었습니다. 서론에서 AI가 만든 코드는 중복과 우회를 남발한다고 했는데, 의도 부채를 줄이려면 그렇게 부채가 될 코드를 애초에 덜 만드는 게 먼저였습니다.

그래서 구현 단계에는 최소 해법 원칙을 상시 적용했습니다. 동작하는 가장 단순한 해법을 쓰고, 새 의존성을 더하기 전에 표준 라이브러리와 언어 기본 기능으로 되는지부터 봅니다. 계획에 없던 추상화나 "나중을 위한" 유연성은 만들지 않습니다.

기록이 이미 생긴 부채의 이자를 갚는 일이라면, 이 원칙은 부채의 원금 자체를 줄이는 일에 가까웠습니다. AI는 요청하면 얼마든지 코드를 더 만들어내기 때문에, 오히려 덜 만들도록 붙잡아 두는 장치가 더 필요했습니다.

## 배운 점

이 작업을 하면서 가장 크게 남은 생각은, AI 시대의 부채는 결과를 얼마나 잘 담보하느냐의 문제가 아니라는 점이었습니다. 결과는 AI가 꽤 잘 냅니다. 문제는 그 결과를 만든 이유가 사람의 머릿속에만 있다가 사라진다는 데 있었습니다.

그래서 맥락 공유는 저절로 되는 일이 아니라, 확정하고 기록하는 지점을 의도적으로 설계해야 남는 것이라고 정리하게 됐습니다. 이슈의 증상 기록과 가설 추적, MR Decisions, plan 문서의 역할 분리, 대형 작업의 브랜치 토폴로지는 모두 "맥락이 어디에 남을지를 미리 정해두는" 같은 목적의 장치였습니다. 그리고 그 앞에는 애초에 부채가 될 코드를 덜 만드는 최소 해법 원칙이 있었습니다. 부채의 원금을 줄이고 남은 이자를 기록으로 갚는 것, 결국 이 두 축이 제가 찾은 답이었습니다.
