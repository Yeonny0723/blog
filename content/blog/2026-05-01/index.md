운영 안정성 시리즈를 이어가며 이번에는 실시간 서비스에서 다중 사용자 동시 이벤트를 어떻게 검증 가능한 형태로 바꿨는지 짚어 보려고 합니다.

이번 글의 출발점은 단순했습니다. 파티룸에서 DJ 등록, 대기열 변경, 채팅 제재, 아바타 반영, 리액션 같은 기능은 모두 "한 명이 버튼을 눌렀을 때 끝나는 기능"이 아니었습니다. 한 사용자의 액션이 서버를 거쳐 다른 사용자의 화면에도 반영되어야 했고 그 과정에서 REST 요청, WebSocket broadcast, 클라이언트 상태 갱신, UI 렌더링이 연쇄적으로 이어졌습니다.

문제는 이 흐름을 수동으로 검증하는 일이 생각보다 훨씬 어렵다는 점이었습니다. 계정이 두 개 이상 필요했고 사용자마다 화면 상태가 미묘하게 달랐습니다. 어느 시점에는 요청은 끝났는데 화면은 아직 준비되지 않은 경우도 있었습니다. "방금은 됐는데 다시 하면 안 되는" 사례도 자주 나왔습니다. 운영 안정성 관점에서 보면 이런 기능은 사람의 손으로 확인하는 순간부터 누락과 착시가 생기기 쉬운 영역이었습니다.

그래서 이번에는 Playwright 기반 E2E 테스트를 도입해, 다중 사용자 동시 이벤트 시나리오를 반복 가능하게 만드는 작업을 진행했습니다. 구축 과정에서는 Playwright MCP로 실제 브라우저 상호작용을 빠르게 재현하고 flaky 구간을 확인했습니다. Notion MCP는 CI 단계에서 Vercel 환경 변수와 GitHub environment 변수를 구분해 정리하는 문서화 용도로만 사용했습니다. 이 글에서는 어떤 시나리오를 자동화 대상으로 삼았는지, 왜 그런 구조로 설계했는지, 그리고 안정화 과정에서 어떤 판단을 했는지 정리해 보겠습니다.

## 왜 수동 검증으로는 버티기 어려웠는가

가장 큰 이유는 "동시에 일어나는 일"을 사람이 정확히 맞춰 보기 어렵기 때문이었습니다.

예를 들어 DJ 대기열 시나리오를 생각해 보면, 한 사용자가 DJ로 등록되고 다른 사용자가 같은 파티룸에 들어와 그 상태를 봐야 합니다. 이후 두 번째 사용자가 대기열에 들어가고 다시 등록을 취소했을 때 두 사용자 화면에서 모두 대기열 UI가 올바르게 갱신되어야 합니다. 이 과정은 단순히 버튼 클릭 몇 번으로 끝나지 않습니다. 한 번의 사용자 액션 뒤에 REST mutation, 서버 처리, broadcast, 구독 중인 다른 클라이언트의 상태 반영이 이어집니다.

수동 검증에서는 보통 이런 문제가 생겼습니다.

- 두 브라우저를 번갈아 보다가 어느 화면이 먼저 바뀌었는지 놓치기 쉬웠습니다.
- 요청은 성공했지만 화면은 아직 준비되지 않은 시점에 다음 액션을 눌러 테스트 자체를 오염시키는 경우가 있었습니다.
- 로컬에서는 재현되는데 staging에서는 느린 응답과 배포 직후 cold-start 때문에 전혀 다른 양상으로 실패하기도 했습니다.
- 한 시나리오만 단독으로 돌릴 때는 통과하지만, 여러 시나리오를 함께 돌리면 flaky하게 실패하는 경우가 있었습니다.

결국 필요했던 것은 "기능이 있다"는 확인이 아니라, "이 상태 전이가 다시 일어나도 같은 결과를 내는가"를 반복해서 검증할 수 있는 장치였습니다.

## 어떤 시나리오를 E2E 대상으로 삼았는가

이번 E2E는 파티룸의 핵심 상호작용을 네 개의 시나리오로 나눠 구성했습니다.

1. `E2E-A`: 파티룸 생성 후 늦게 입장한 사용자가 현재 재생 상태를 정상적으로 동기화받는지 검증했습니다.
2. `E2E-B`: DJ 등록, DJ 대기열 진입, 대기열 취소가 두 사용자 화면에 동시에 반영되는지 검증했습니다.
3. `E2E-C`: block, kick, ban과 같은 moderation 흐름이 각 사용자 화면과 재입장 정책에 정확히 반영되는지 검증했습니다.
4. `E2E-D`: 프로필 아바타 변경, 현재 DJ 아바타 반영, 리액션, 채팅 송신까지 한 사용자의 상태 변경이 UI에 이어지는지 검증했습니다.

여기서 중요했던 점은 "화면 하나를 넓게 훑는 테스트"를 만들지 않는 것이었습니다. 각 시나리오는 한 번에 모든 기능을 확인하려 하지 않고 특정 상태 전이 하나만 책임지도록 나눴습니다. 예를 들어 `E2E-B`는 DJ 상태 머신과 다중 클라이언트 동기화에만 집중했습니다. 그래야 실패했을 때도 무엇이 깨졌는지 해석할 수 있었습니다.

## 시나리오 선정이 사실상 이 작업의 핵심이었습니다

E2E를 붙이는 것보다 어려운 판단은, 무엇을 자동화 대상으로 삼을지 정하는 일이었습니다. 도구는 정해지면 따라오지만, 검증 범위는 누가 대신 정해 주지 않습니다.

먼저 연계된 인프라를 지나는 흐름을 따로 구분해내야 했습니다. 한 기능이 프론트 클릭에서 끝나지 않고 서버, broadcast, 외부 서비스까지 이어질 때, 그 종단간 경로 하나를 검증 단위로 떼어내는 일이 시작점이었습니다. 이런 흐름일수록 수동으로는 중간 어디서 끊겼는지 알기 어렵기 때문입니다.

그다음은 그중에서 핵심 도메인 시나리오를 뽑아내는 일이었습니다. 모든 경로를 자동화하는 것은 의미가 없었고, 깨지면 서비스가 실제로 흔들리는 흐름을 골라야 했습니다. 응답이 지연되어 "몇 초, 때로는 몇 분까지를 성공으로 보고 그 뒤를 실패로 볼지" 기준을 정해야 하는 구간이 대표적이었습니다.

이 선별은 결국 도메인을 충분히 이해해야 가능한 일이었습니다. 어떤 흐름이 정말 검증할 가치가 있는지는 도구가 아니라 그 제품과 인프라를 잘 아는 사람만 판단할 수 있는 영역이었습니다.

## 설계의 핵심은 다중 사용자 컨텍스트였습니다

이 테스트에서 가장 중요한 요구사항은 서로 다른 두 사용자가 같은 시나리오 안에서 동시에 살아 있어야 한다는 점이었습니다. 그래서 Playwright의 `BrowserContext`를 사용자 단위 세션으로 사용했습니다.

각 시나리오는 `auth/setup.<scenario>.ts`에서 필요한 계정의 로그인 세션을 먼저 저장해 두고, 실제 테스트에서는 `storageState`를 복원해 `user1Context`, `user2Context`를 만들었습니다. 매 테스트마다 로그인 UI를 처음부터 다시 밟지 않도록 한 이유는 두 가지였습니다.

- 로그인 자체가 테스트의 본질이 아니었습니다.
- 매번 로그인하면 느리고, dev 로그인 플로우가 흔들릴 때 실제 시나리오와 상관없는 실패가 늘어났습니다.

이 구조 덕분에 한 테스트 안에서 `user1`과 `user2`가 서로 다른 브라우저 컨텍스트를 유지한 채 같은 파티룸에 들어가고, 각 화면에서 상태가 어떻게 달라지는지 독립적으로 확인할 수 있었습니다.

특히 `E2E-B`에서는 이 구조가 핵심이었습니다. 한 사용자가 DJ가 되면 다른 사용자 화면에도 현재 DJ가 보여야 했습니다. 두 번째 사용자가 대기열에 들어갔다가 취소하면 양쪽 화면에서 대기열 아이템 수가 모두 0으로 돌아가야 했습니다. 이런 흐름은 단일 사용자 테스트로는 검증할 수 없었습니다.

## 중요한 것은 "클릭"이 아니라 "준비 완료"를 기다리는 기준이었습니다

초반에 가장 많이 부딪힌 문제는, 사용자가 버튼을 눌렀다는 사실과 화면이 다음 상태를 받아들일 준비가 되었다는 사실이 다르다는 점이었습니다.

예를 들어 파티룸에 입장했다고 해서 곧바로 다음 액션을 눌러도 되는 것은 아니었습니다. 파티룸 진입 후 버튼이 보이는지, WebSocket 구독이 완료되었는지, 특정 초기 응답이 반영되었는지까지 기다려야 했습니다. 그래서 단순한 `waitForTimeout`에 기대기보다, 시나리오별 준비 완료 조건을 helper에 모았습니다.

대표적으로 `enterPartyroomAndWaitUntilReady()`에서는:

- 파티룸 진입 URL이 맞는지 확인하고
- `DJ Queue` 버튼이 실제로 보이는지 기다리고
- 클라이언트 내부에 구독된 파티룸 ID가 기대값과 일치하는지 `expect.poll`로 확인했습니다

이런 식으로 "무엇을 기다릴 것인가"를 명확히 정리해 두지 않으면, 테스트는 쉽게 클릭 자동화 스크립트가 되어버립니다. 그리고 그런 테스트는 네트워크 상태가 조금만 달라져도 바로 깨집니다.

물론 중간중간 짧은 대기 시간도 일부 남겼습니다. 예를 들어 DJ 대기열 취소 직전 2초 정도 쉬는 구간이 있습니다. 다만 이 대기는 주된 동기화 수단이 아니라, 이미 명시적인 준비 조건을 통과한 뒤 UI 전환의 흔들림을 완충하는 보조 장치로만 사용했습니다.

## selector도 운영 안정성 관점에서 골랐습니다

E2E를 만들면서 selector 전략도 꽤 중요했습니다. 테스트가 UI 구현 세부사항에 과하게 묶이면, 기능은 멀쩡한데 마크업이 조금만 바뀌어도 테스트가 깨지기 때문입니다.

그래서 우선순위를 분명히 뒀습니다.

- 먼저 `getByRole`을 사용했습니다.
- 텍스트나 라벨로 충분할 때는 `getByText`, `getByLabel`, `getByPlaceholder`를 사용했습니다.
- 동적 count, hover 메뉴, 반복 리스트, overlay처럼 role만으로 안정적으로 잡기 어려운 영역에만 `data-testid`를 허용했습니다.

예를 들어 crews 탭처럼 라벨 자체가 동적으로 바뀌는 영역은 `data-testid`가 더 안정적이었습니다. 반대로 채팅 탭, 버튼, 다이얼로그처럼 의미가 분명한 요소는 role 기반 선택자가 더 오래 버텼습니다.

이 기준을 둔 이유는 단순합니다. 테스트를 위해 공용 컴포넌트 API를 오염시키고 싶지 않았기 때문입니다. 공용 컴포넌트마다 테스트 전용 prop이 번지기 시작하면, 테스트는 편해질지 몰라도 제품 코드가 지저분해집니다. 그래서 feature 레벨 container에만 필요한 selector를 두고, 내부는 role과 text 기반으로 마무리하는 쪽을 우선했습니다.

## preview 환경을 직접 검증하는 흐름까지 연결했습니다

로컬에서만 통과하는 E2E는 운영 안정성 측면에서 반쪽짜리에 가깝다고 봤습니다. 방금 배포된 preview를 기준으로 테스트가 돌아야 했습니다.

그래서 GitHub Actions에서 preview 배포 후 바로 Playwright E2E를 실행하는 워크플로우를 만들었습니다. 흐름은 다음과 같습니다.

1. `development` 브랜치에 push합니다.
2. GitHub Actions가 Vercel Preview를 배포합니다.
3. 방금 배포된 preview를 `stg.pfplay.xyz`에 alias로 연결합니다.
4. E2E는 `https://stg.pfplay.xyz`를 기준으로 실행합니다.

이 구조가 필요했던 이유도 분명했습니다. 백엔드 스테이징 서버가 `stg.pfplay.xyz` origin만 허용하고 있었기 때문에, 일반적인 `*.vercel.app` preview URL로는 API 호출이 막혔습니다. 결국 "방금 배포한 코드를 검증하되, 백엔드가 허용하는 origin으로도 접속 가능해야 하는" 조건을 만족하려면 alias가 필요했습니다.

이 판단 덕분에 테스트의 기준점도 분명해졌습니다. 로컬에서 마지막으로 띄운 서버가 아니라, 방금 배포된 preview가 항상 검증 대상이 되었습니다.

안정화 과정에서는 "준비가 끝난 상태"를 어디까지 볼 것인지 계속 다시 정의해야 했습니다.

예를 들어 로그인 직후 세션이 있다고 해서 곧바로 다음 단계를 시작할 수 있는 것은 아니었습니다. sidebar가 아직 mount되지 않았거나, 필요한 초기 쿼리가 덜 끝난 상태일 수 있었습니다. 이런 상황에서는 테스트가 실패해도 원인이 시나리오 자체인지, 준비되지 않은 환경 때문인지 분간하기 어려웠습니다.

- DJ Queue drawer가 이미 열려 있는지 먼저 확인하고, 열리지 않았을 때만 보조 클릭 경로를 타도록 helper를 정리했습니다.
- drawer를 닫을 때도 단순 `click`으로 끝내지 않고 실제로 닫힐 때까지 polling 하도록 바꿨습니다. Headless UI dialog가 열린 동안 다른 영역이 inert 처리되기 때문에, drawer가 덜 닫힌 상태로 다음 step으로 넘어가면 `My profile` 같은 버튼이 role query에 잡히지 않는 문제가 있었습니다.
- preview와 staging 조합에서 응답이 느려지는 cold-start를 흡수하기 위해 HTTP timeout을 환경변수로 조정할 수 있게 했습니다.
- `E2E-B`의 `beforeAll`은 두 사용자 플레이리스트 생성과 파티룸 생성까지 모두 포함하므로 timeout을 더 넉넉하게 잡았고 CI에서는 workers를 1로 직렬화해 cold-start 간섭을 줄였습니다.

이 지점이 중요했던 이유는, flaky 테스트의 원인이 항상 "테스트 코드가 부정확해서"만은 아니기 때문입니다. 어떤 실패는 실제 UI 상태 전이 문제이고, 어떤 실패는 배포 직후 인프라 응답 특성 때문에 생깁니다. 둘을 구분하지 않으면 잘못된 처방을 하게 됩니다.

여기에 더해 preview 보호를 우회하려고 넣은 헤더가 제3자 리소스 요청에까지 영향을 줄 수 있다는 점도 고민이었습니다. 테스트 환경에서는 편의를 위해 전역 헤더 주입을 선택하기 쉽지만 이런 방식은 YouTube 같은 cross-origin 요청을 예상과 다른 형태로 바꿔 또 다른 flaky 원인을 만들 수 있습니다. 운영 환경과 유사한 E2E를 만들고 싶을수록, 테스트 편의용 우회 설정이 어디까지 전파되는지 함께 봐야 했습니다.

## Playwright MCP를 쓴 이유

이번 작업에서 Playwright MCP는 단순히 브라우저를 대신 눌러주는 도구가 아니라, flaky 구간을 좁히는 데 도움이 되는 탐색 도구에 가까웠습니다.

- 어떤 버튼이 실제로 보이는지
- overlay가 아직 남아 있는지
- 특정 시점에 어떤 응답이 먼저 도착하는지
- role 기반 selector로 충분한지, 아니면 별도 anchor가 필요한지

이런 문제는 코드만 읽어서는 놓치기 쉬웠습니다. 실제 브라우저 상태를 보면서 실패 지점을 확인하고 그걸 helper와 selector 기준으로 다시 정리하는 과정이 필요했습니다.

## 구축하면서 배운 점

이번 작업에서 가장 크게 느낀 점은 세 가지였습니다.

첫째, 실시간 다중 사용자 시나리오는 수동 QA에 의존할수록 불확실성이 커집니다. 재현이 어렵고, 사람의 기억과 타이밍에 기대게 되기 때문입니다.

둘째, E2E의 핵심은 많은 화면을 누르는 것이 아니라 "다음 액션을 해도 되는 시점"을 정의하는 것입니다. 준비 완료 조건이 없으면 테스트는 곧 flaky해집니다.

셋째, 운영 안정성 관점의 E2E는 로컬만 통과해서는 부족합니다. 배포 직후 환경에서, origin 제약과 응답 지연까지 포함한 상태로 돌려봐야 의미가 있습니다.

여기에 하나를 더 보태면, flaky를 줄이는 일은 대기 시간을 무작정 늘리는 일이 아니었습니다. "무엇이 아직 준비되지 않았는가"를 더 정확히 설명하는 작업에 가까웠습니다. Playlist 버튼이 아예 아직 mount되지 않은 상태인지, drawer가 transition 중이라 접근성 트리에서 다른 버튼을 가리고 있는지, 혹은 CI에서 두 worker가 동시에 워밍되지 않은 백엔드를 두드리고 있는지 구분해야 했습니다.

## 같은 고민을 하는 분들에게

비슷한 실시간 서비스를 운영하고 있다면, 처음부터 거대한 E2E 묶음을 만들기보다 아래 기준으로 시작하는 편이 좋다고 생각합니다.

1. 한 번의 사용자 액션 뒤에 다른 사용자의 화면이 바뀌는 시나리오부터 고릅니다.
2. 로그인 자체보다 본질적인 상태 전이에 집중할 수 있도록 인증 세션을 재사용합니다.
3. `waitForTimeout`보다 "이 상태가 준비되었는지"를 판별하는 조건을 helper로 먼저 만듭니다.
4. selector는 role 기반을 우선하고, 정말 필요한 곳에만 `data-testid`를 둡니다.
5. 가능하면 방금 배포된 preview를 기준으로 돌려, 로컬과 다른 실패를 빨리 발견합니다.

## 마치며

이번 E2E 작업은 테스트 도구를 하나 더 붙인 일이라기보다, 실시간 동시 이벤트를 사람이 아닌 시스템이 반복해서 검증할 수 있게 만든 작업에 가까웠습니다.

특히 DJ 큐, moderation, late join sync처럼 한 사용자 화면만 봐서는 판단하기 어려운 기능은 E2E를 붙인 뒤에야 비로소 "운영 가능한 수준으로 검증된다"는 느낌이 있었습니다.

운영 안정성은 결국 장애가 났을 때만 다루는 문제가 아니라, 평소에 얼마나 재현 가능하고 반복 가능한 검증 경로를 만들었는가의 문제인 것 같습니다. 이번 글이 다중 사용자 실시간 기능을 다루는 분들께 조금이라도 구체적인 참고가 되었으면 합니다.
